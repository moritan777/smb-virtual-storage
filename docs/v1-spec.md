# SMB Virtual Storage — V1 Specification

## 1. 文書の目的

本書は、Android端末から自宅等のSMB共有上に存在するファイルを、Androidのストレージの一部に近い感覚で利用するためのアプリケーション「SMB Virtual Storage（仮称）」のV1仕様を定義する。

本書はV1の**機能仕様の正本**とする。

実装方式、ライブラリ選定、クラス構成等の技術設計は別途 `docs/architecture.md` で定義する。

---

# 2. 背景

microSD非対応のAndroid端末では、大量の音楽、漫画、PDF、動画等を端末内へ保持することが難しい。

一方、自宅にSMB対応NAS/ファイルサーバーが存在する場合、一般的なSMB対応ファイルマネージャーを利用してファイルへアクセスすることは可能である。

しかし一般的なSMBファイルマネージャーでは、NASは「ファイルマネージャーアプリ内部のネットワーク上の場所」として扱われる。

本プロジェクトではこれとは異なり、

> **SMB共有そのものをAndroidのストレージProviderとして公開する**

ことを目的とする。

AndroidのStorage Access Framework（SAF）からNAS上のファイルを参照できるようにし、利用者から見て「読み取り専用の仮想SDカード」に近い操作感を実現する。

---

# 3. V1の基本コンセプト

V1のコンセプトを次のように定義する。

> **SMB共有をAndroid上にread-onlyの仮想ストレージとして公開し、必要になったファイルのみ端末へオンデマンドで完全取得して利用する。**

V1ではSMB共有上のファイルを直接編集しない。

ファイルを開く際は、SMB上のファイルを端末へ全量ダウンロードし、ローカルキャッシュ完成後に対象アプリへ提供する。

---

# 4. 想定利用環境

主な対象はAndroidスマートフォンおよびタブレットとする。

主要な想定環境は以下。

- Android端末
- SMB2/SMB3対応NASまたはファイルサーバー
- LANまたはVPN等を通じてSMBサーバーへ到達可能なネットワーク

初期開発および実機評価ではPixel 9aを主要検証端末とする。

ただし、特定のPixel機能への依存を前提としない。

---

# 5. 想定ユースケース

V1では特に以下の利用を想定する。

### 5.1 自炊漫画

SMB上に保存されたZIP/CBZ等の漫画ファイルをAndroidから選択し、漫画リーダーで読む。

1冊の漫画ファイルは全量取得してから漫画リーダーへ提供する。

### 5.2 PDF・電子書籍・文書

SMB上のPDF等をAndroidのファイル選択UIから選択し、対応アプリで閲覧する。

### 5.3 その他のread-onlyファイル

AndroidアプリがStorage Access Framework経由で読み込めるファイルを対象とする。

---

# 6. Android上での見え方

SMB共有はAndroidのStorage Access FrameworkへDocumentsProviderとして公開する。

利用者からは概念的に以下のように見えることを目標とする。

```text
Files

├─ Pixel 9a
│   ├─ Download
│   ├─ Documents
│   └─ ...
│
├─ NAS Manga
│   ├─ Series A
│   ├─ Series B
│   └─ ...
│
├─ NAS Music
│   └─ ...
│
└─ NAS Documents
    └─ ...
```

SMB共有はAndroid内部ストレージへ物理的にマウントされるわけではない。

したがって、本物のSDカードのような `/storage/XXXX-XXXX/` のファイルシステムパスを提供することはV1の目的としない。

SAF対応アプリから利用可能な仮想ストレージとして提供する。

---

# 7. 複数SMB共有

複数のSMB共有を登録可能とする。

各共有は独立したStorage Access Framework上のrootとして公開できる設計とする。

例：

```text
NAS Manga
NAS Music
NAS Documents
NAS Archive
```

複数共有を強制的に1つの仮想ディレクトリへ統合することはV1では行わない。

---

# 8. Read-only

V1ではSMB共有を完全なread-onlyとして扱う。

V1で許可する操作：

- フォルダ一覧取得
- ファイル一覧取得
- ファイル情報取得
- ファイル読み込み
- ローカルキャッシュへの取得
- キャッシュ済みファイルの読み込み

V1では以下を実装しない。

- 新規ファイル作成
- SMBへの書き込み
- 上書き
- 削除
- rename
- move
- SMB側ディレクトリ作成

ただし、これらは永久に非対応とするものではない。

将来的なwrite対応を妨げない内部設計とする。

---

# 9. ファイル取得方式

V1ではファイル単位で取得する。

部分取得・ブロックキャッシュ・ストリーミング読み込みは行わない。

ファイルを開く処理は以下とする。

```text
ユーザーがファイルを選択
        ↓
キャッシュ確認
        ↓
有効なキャッシュなし
        ↓
SMBからファイル全量取得
        ↓
ローカルキャッシュへ保存
        ↓
取得完了
        ↓
対象アプリへファイルを提供
```

ファイル取得途中に対象アプリへ不完全なデータを渡さない。

---

# 10. ローカルキャッシュ

SMBから取得したファイルは端末内へキャッシュする。

キャッシュ単位は**ファイル単位**とする。

例えば300MBの漫画ZIPを開いた場合、300MBのファイル全体をローカルキャッシュへ保存する。

次回同じファイルを開く場合、有効なキャッシュが存在すればSMBから再取得せずローカルキャッシュを利用する。

---

# 11. キャッシュ有効性

SMB側ファイルが変更された場合、古いキャッシュを利用し続けないようにする。

V1では少なくとも以下の情報を利用してキャッシュの有効性を判断する。

- SMB上のファイルパスまたは安定した識別情報
- ファイルサイズ
- lastModified

概念的には、

```text
path
+
size
+
lastModified
```

が一致していれば同一バージョンのファイルとして扱う。

毎回ファイル全体のハッシュを計算する方式はV1では必須としない。

---

# 12. キャッシュ容量管理

キャッシュには容量上限を設ける。

容量上限を超える場合はLRU（Least Recently Used）方式を基本として、最後に利用された時刻が古いキャッシュから削除する。

キャッシュ容量の具体的な初期値および設定UIは設計段階で決定する。

V1では少なくとも、

- 現在のキャッシュ使用量
- キャッシュ上限
- キャッシュ削除

を管理可能な設計とする。

---

# 13. オフライン動作

SMBサーバーへ接続できない場合でも、有効なローカルキャッシュが存在するファイルは開けるものとする。

```text
SMB接続不可
     │
     ├─ 有効キャッシュあり
     │        ↓
     │      開ける
     │
     └─ キャッシュなし
              ↓
          開けない
```

未キャッシュファイルを開こうとした場合は、SMB/NASへ接続できないことを利用者へ明確に通知する。

---

# 14. ダウンロード完了前の扱い

V1ではファイルを全量取得してから対象アプリを起動する。

漫画ZIP、PDF等について、ダウンロード途中から閲覧可能にする機能は実装しない。

そのためV1では以下を対象外とする。

- HTTP Range相当の部分取得
- SMBランダムアクセスを対象アプリへ直接公開
- ストリーミング読み込み
- ZIPの部分取得
- 読みながら次ブロックを取得する仕組み

---

# 15. ダウンロード中UI

ファイル取得には時間がかかる可能性があるため、利用者が現在の状態を把握できることを必須とする。

少なくとも以下を識別可能にする。

- 取得開始
- 取得中
- 取得完了
- 取得失敗
- キャンセル

詳細なUI表現は設計段階で決定する。

ダウンロード途中の不完全なファイルを正常キャッシュとして扱ってはならない。

---

# 16. アイコン・サムネイル

V1ではファイル内容からのサムネイル生成を行わない。

漫画ZIPの表紙抽出、PDFプレビュー、画像サムネイル等は対象外とする。

V1ではファイル種別または一般的なファイルアイコンによる表示のみとする。

将来的なサムネイル対応を妨げない設計とする。

---

# 17. 音楽関連機能

SMB上の音楽ファイルを扱う可能性はあるが、音楽向け最適化はV1では保留とする。

特に以下はV1では実装しない。

- 次曲先読み
- アルバム単位キャッシュ
- ギャップレス再生支援
- ストリーミング再生最適化
- 音楽ライブラリスキャン最適化

通常のread-onlyファイルとして扱える範囲を超えた音楽固有処理は、将来バージョンで検討する。

---

# 18. ネットワーク

アプリはSMBサーバーへIPネットワーク上で到達可能であることを前提とする。

利用経路は限定しない。

例：

```text
自宅Wi-Fi
    ↓
LAN
    ↓
SMB
```

または、

```text
外出先
    ↓
Tailscale / WireGuard / その他VPN
    ↓
自宅ネットワーク
    ↓
SMB
```

VPN機能そのものは本アプリの責務としない。

アプリ内部に独自VPNを実装しない。

---

# 19. SMBのインターネット直接公開

本アプリはSMBポートをインターネットへ直接公開する運用を前提としない。

外部ネットワークから利用する場合は、VPN等の安全なネットワーク経路によってSMBサーバーへ到達することを想定する。

---

# 20. SMB接続

V1ではSMB2/SMB3を対象とする。

SMB1を必須対応としない。

接続に必要となる基本情報は以下を想定する。

- Host
- Port
- Share
- Username
- Password
- 表示名

具体的な認証情報保存方式は技術設計段階で決定する。

---

# 21. エラー処理

少なくとも以下の状況を区別して処理できること。

- SMBサーバーへ到達不能
- SMB認証失敗
- SMB共有が存在しない
- ファイルが存在しない
- ファイル取得途中で通信切断
- ローカルストレージ容量不足
- キャッシュ書き込み失敗
- SMB側ファイルが取得途中で変更された可能性
- ユーザーによる取得キャンセル

エラー発生時に不完全なファイルを正常キャッシュとして登録してはならない。

---

# 22. 将来のWrite対応

V1ではwriteを実装しないが、将来的に以下を追加する可能性がある。

- create
- write
- overwrite
- delete
- rename
- move
- directory creation
- オフライン編集
- 再接続後の同期
- 競合検出
- 競合解決

したがって内部ストレージ層は、read-only実装そのものと「ストレージは永久にread-onlyである」という前提を混同しないこと。

例えば将来的にStorage Backendが、

```text
list
stat
openRead

create
openWrite
delete
rename
```

等へ拡張可能な責務分離を維持する。

V1ではwrite系操作をUnsupportedとして扱える構造が望ましい。

---

# 23. 将来のPin機能

将来的に「この端末に保持」機能を追加する可能性がある。

通常キャッシュ：

```text
アクセス
 ↓
キャッシュ
 ↓
LRU削除対象
```

Pinned：

```text
「この端末に保持」
 ↓
キャッシュ
 ↓
LRU削除対象外
```

V1ではPin UIを必須としない。

ただし、キャッシュ管理設計が将来のPinned状態追加を妨げないこと。

---

# 24. V1で実装しないもの

以下を明示的にV1対象外とする。

- SMBへの書き込み
- ファイル削除
- rename / move
- SMB側ディレクトリ作成
- オフライン編集
- ファイル競合解決
- ファイル同期エンジン
- SMBストリーミング
- 部分ファイルキャッシュ
- 音楽先読み
- 動画ストリーミング最適化
- サムネイル生成
- VPN機能
- SMB以外のストレージBackend
- root権限を利用した実ファイルシステムmount

---

# 25. V1で実現したい利用体験

利用者がAndroidのFilesまたはSAF対応アプリから、

```text
NAS Manga
```

を開く。

NAS上のフォルダを通常のフォルダのように移動する。

```text
NAS Manga
└─ Series A
    ├─ Volume 01.zip
    ├─ Volume 02.zip
    └─ Volume 03.zip
```

`Volume 01.zip` を選択する。

未キャッシュの場合：

```text
SMB
 ↓
Volume 01.zip 全量取得
 ↓
ローカルキャッシュ完成
 ↓
漫画リーダーへ提供
```

キャッシュ済みの場合：

```text
ローカルキャッシュ
 ↓
漫画リーダーへ提供
```

外出先等でNASへ到達できなくても、有効なキャッシュが存在すれば同じファイルを開ける。

---

# 26. V1の成功条件

V1完成の最低条件を以下とする。

1. AndroidのStorage Access Frameworkから登録したSMB共有がrootとして見える。
2. SMB上のフォルダを移動できる。
3. SMB上のファイル一覧を取得できる。
4. V1では書き込み操作が提供されない。
5. 未キャッシュファイルを選択するとSMBから全量取得される。
6. 全量取得完了後に対象アプリから読み込める。
7. キャッシュ済みファイルは再ダウンロードせず開ける。
8. SMB側ファイルが変更されていれば古いキャッシュを無効化できる。
9. キャッシュ容量を管理できる。
10. 上限超過時にLRUでキャッシュを整理できる。
11. SMBへ接続できなくても有効キャッシュ済みファイルは開ける。
12. SMBへ接続できずキャッシュも存在しない場合は明確に失敗する。
13. 通信切断やキャンセルで生じた不完全ファイルを正常キャッシュとして扱わない。
14. 複数SMB共有を登録できる。
15. 将来のwrite対応を阻害する構造になっていない。

---

# 27. V1の設計原則

V1の実装では以下を優先する。

**単純性**

部分取得や同期等を早期に導入せず、ファイル単位全量取得を基本とする。

**安全性**

V1ではSMBをread-onlyとし、NAS上の原本を破損する可能性を極力排除する。

**互換性**

独自ファイルUIだけに閉じず、Android Storage Access Frameworkを利用する。

**責務分離**

SMB、キャッシュ、DocumentsProvider、UI、ネットワーク経路を必要以上に結合しない。

**将来拡張**

V1の単純化を理由として、将来のwrite、Pin、音楽最適化等を不必要に困難にする構造を採用しない。

# 29. 仕様変更の扱い

本書に記載されたV1範囲を変更する場合は、実装コードだけを先行して変更せず、本仕様書を更新する。

特に以下を無断でV1へ追加しない。

- write
- delete
- rename
- sync
- streaming
- thumbnail
- VPN
- 音楽固有最適化

実装上便利であることのみを理由としてV1の責務を拡大しない。
